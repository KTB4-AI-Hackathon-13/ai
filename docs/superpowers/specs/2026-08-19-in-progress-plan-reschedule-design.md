# 진행 중인 장기 계획 재조정 설계

## 배경

확정되어 실행 중인 장기 계획(예: 30일)의 일부 구간을 사용자가 채팅방으로 돌아와 재조정 요청할
수 있다(예: "11일부터 20일까지만 좀 가볍게 다시 짜줘"). FE는 사용자가 각 task를 완료/건너뜀
처리하는 걸 이미 추적하고 있으므로, 이 케이스는 **새 엔드포인트나 스키마 변경 없이** 기존
`/plan/revise`를 그대로 재사용한다.

## 핵심 아이디어

`current_plan`은 "직전 턴에 보여준 계획 전체"가 아니라 "현재 남아있는(미완료) 계획 상태"로
취급한다는 게 원래 `/plan/revise`의 설계 의도이며, 이건 이미 성립한다. 여기에 필요한 건 딱
하나 — LLM이 "current_plan에 없는 날짜 = 이미 끝났거나 건드리지 않을 부분"이라는 걸 명시적으로
알게 하는 프롬프트 규칙뿐이다.

## 데이터 흐름

```
FE (task 완료/건너뜀 추적)
   │  BE가 완료된 task를 제외하고 필터링
   ▼
PlanReviseRequest {
  template_answers: 원래 목표의 전체 기간(예: 1~30일차) — 그대로, 좁히지 않음
  current_plan:     아직 완료되지 않은 task만 (예: 11~30일차)
  user_message:     "11일부터 20일까지만 다시 짜줘" — 자연어로 조정 대상 구간을 지정
}
   │
   ▼
기존 /plan/revise 로직 (변경 없음) — 규칙 1("요청과 무관한 부분은 유지")에 따라
user_message가 지목한 11~20일차만 조정하고, 21~30일차는 current_plan 그대로 반환
```

`template_answers`는 원래 전체 기간을 유지해야 한다 — 이걸 재조정 대상 구간(11~20일)으로
좁혀 보내면, `current_plan`에 남아있는 다른 미완료 task(21~30일차)의 날짜가 "범위 밖"으로
보여 LLM이 혼란을 겪을 수 있다. `template_answers`는 좌표계(전체 유효 기간) 역할이고,
"어디를 실제로 고칠지"는 오직 `user_message`(자연어)로만 지정한다.

## 스키마 변경

없음. `DailyTask`/`SchedulePlan`은 완료 상태 개념을 아예 모른다 — FE/BE가 완료된 task를
필터링해서 AI에게 애초에 안 보여주는 방식으로 처리하므로, AI가 완료 여부를 오판할 여지 자체가
없다.

## 프롬프트 변경 (`app/plan_generation/prompts.py` — `PLAN_REVISE_SYSTEM`)

규칙 추가:

> current_plan은 이 목표의 전체 계획이 아니라 아직 완료되지 않은 남은 구간만 담고 있을 수
> 있다. current_plan에 없는 날짜는 이미 완료되었거나 사용자가 다루지 않기로 한 부분이니
> 새로 만들어내거나 채워 넣지 않는다. user_message가 특정 날짜 구간만 지목하면 그 구간만
> 조정하고, current_plan에 있는 나머지 날짜는 그대로 유지한다.

## 확정 시 동작

변경 없음. 기존 `user_confirmed` 자동 감지 로직이 그대로 적용되어, 사용자가 확정 의사를
밝히면 `req.current_plan`(=조정된 남은 구간)이 그대로 `submit_final_plan(schedule_id,
current_plan)`으로 BE에 전송된다.

**전제(BE 책임, 이 레포 범위 밖)**: BE는 이 `submit_final_plan` 호출을 "새 스케줄 생성"이
아니라 "기존 `schedule_id`의 남은 구간을 갱신(교체)"으로 처리해야 한다. 이미 완료된
1~10일차는 BE가 별도로 보존하고, AI가 돌려준 건 어디까지나 "남은 구간의 새 버전"이라는 걸
BE가 인지하고 병합해야 한다.

## 테스트 계획 (`tests/plan_generation/test_service.py`)

- `current_plan`이 목표 전체가 아닌 일부(예: 11~30일차)만 담고 있어도 `revise_plan`이
  에러 없이 정상 동작하는지 확인 (기존 로직 재사용 확인용 회귀 테스트)
- 프롬프트 규칙 자체가 실제로 잘 지켜지는지(LLM이 정말 지목 안 된 날짜를 안 건드리는지)는
  `pytest -m live` 또는 수동 확인 영역 — 유닛 테스트로는 검증하지 않는다

## 범위 밖

- BE가 `submit_final_plan` 결과를 기존 완료 이력과 병합하는 로직 (다른 레포)
- `DailyTask`에 완료 상태 필드 추가 — 이번 설계로 불필요하다고 결론남 (FE/BE 필터링으로 대체)
